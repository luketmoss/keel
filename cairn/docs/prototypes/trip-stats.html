Where the numbers come from

KML carries four of the five, conditionally

Coordinates are lon,lat,alt; altitude is the optional third component. Whether it's there is a property of the export format, not the vendor that produced it. Gaia and CalTopo's KML exports use <gx:Track>, which carries altitude and <when> timestamps, and togeojson already flattens it into the LineString that parse.ts reads. Distance is always computable. Ascent, descent, high point and low point exist only when that third component genuinely does.

Garmin Connect's own KML ("Export to Google Earth") is the counter-example worth knowing by name: every one of its 358 points in a 5.19-mile hike was a plain 2-component lon,lat tuple, no <gx:Track>, no <when>, and <altitudeMode>clampToGround</altitudeMode> set at the document level. The only elevation figures in the file are HTML text inside lap descriptions (Elevation Gain : 1952 Feet), which the app does not parse — see Out of Scope in #222. For a file shaped like this, distance-only is the correct read, not a defect: Garmin's own GPX and TCX exports do carry elevation, so the fix is picking a different export from the same watch, not a bug in this app.

All-identical altitudes mean unavailable, not flat

KML's default altitudeMode is clampToGround, and exporters that intend clamping write 0 for every point rather than omitting the component. Google My Maps does exactly this. The existing "fewer than two points carry elevation" rule does not catch it, so the trip would claim 0 ft ↑ — an assertion, not a gap. altitudeMode itself is not checkable, because togeojson discards it before the parser sees the geometry.

The rule: if every elevation value in a track is identical, that track's elevation is unavailable. A real GPS track — even a dead-flat one — never produces identical consecutive values, so there is no false negative to trade against. Panel C is this case.

Two constants, and why #7's "no smoothing" line retires

7-track-statistics.md took raw positive deltas with no threshold, flagged as accepted v1 behaviour to be revisited "when a real file reads implausibly rather than pre-emptively". Showing descent and a high point next to ascent is that moment, for two different reasons.

ConstantValueWhat it fixes
ELEVATION_MEDIAN_WINDOW 5 A single spike sample sets the high point. 14,410 ft on a 14,153 ft summit is instantly wrong to anyone who walked it, because there is a published number to check it against — where an inflated ascent figure has nothing to fail against. A median rejects isolated spikes; a mean would smear the summit down instead. It also keeps the profile from drawing visibly hairy, which is the reason this cannot be deferred once the profile exists.
ELEVATION_THRESHOLD_METERS 3 Hysteresis against a reference elevation, rather than summing every positive delta: a change commits only once the series leaves a ±3 m band. Consumer GPS vertical error runs 5–15 m and barometric 1–3 m, and KML does not say which you got, so 3 m is the conservative floor. It also disposes of a device recording at 1 Hz through a lunch stop — hundreds of deltas, zero distance, none of which ever leave the band.

Filter first, then accumulate. Both constants live in one block at the top of stats.ts, commented the way SYSTEM is in units.ts — #7's principle is that a number the user can see is debuggable and a silently clamped one is not, and a smoothed figure is only honest if the smoothing is one obvious constant rather than arithmetic scattered through a loop.

The invariant this buys, which raw summing has no version of: on a closed loop, ascent and descent differ only by the start/end elevation difference. That is checkable against a real file rather than eyeballed, and putting the two numbers side by side is what makes a violation visible.

Totals

Distance sums over every track. Ascent and descent sum, and high and low take the max and min, over only the tracks carrying elevation — with the count of those tracks stated beneath the grid whenever it is not all of them. A total silently computed over a subset is the failure mode the footnote exists to prevent.

Not taken: the Elevation API

Sampling Google's Elevation API against a DEM would beat filtered GPS altitude outright and is vendor-consistent with the map. Held back because it is per-track network work on a quota against a project whose stated architecture puts nothing but storage on the wire; because it is wrong, and silently so, for anything genuinely off the ground; and because it does not help panel C at all — a drawn My Maps route has no track to sample honestly. It is the upgrade path once a real file reads implausibly after the two constants above, not the v1.
